# 0111 - the SDK already has a word for it

Six bytes, and they buy a customer one vocabulary instead of two. The selection table offers a row
for an agent whose output is a run of tools, and until now the value typed under that row was spelled
`final-state` while the product had shipped `state_transition` for the identical idea since its
verifier kinds were defined. Nobody reading the SDK first would guess ours, and nobody reading ours
first would recognise theirs. The rendering rule is mechanical - kebab-case whatever word the product
already uses - so the guide stops minting synonyms for concepts that are already named, and the row's
prose is moved onto the same word so that the sentence and the value a reader types no longer differ.

Why the arithmetic is so small, when a rename usually is not. The typed value lives in exactly one
assistant-facing line; everything else that carries it is a script constant, a payload key or a test,
and none of those is measured here. So the whole guidance cost of the alignment is the difference in
length between two spellings on a single table row, and it is stated in its own entry rather than
folded into a neighbour because a vocabulary decision is worth finding later on its own terms.

Now rather than later is the argument for spending anything at all. These are values a customer types
and then keeps - in a script, in a note, in a message to a colleague - so the price of correcting them
rises from the first person who writes one down, and almost nobody has yet. The companion value moves
the other way and costs nothing here: `--task-kind` drops to the product's own `tool`, which is
shorter than what it replaces and appears in no measured document at all.
