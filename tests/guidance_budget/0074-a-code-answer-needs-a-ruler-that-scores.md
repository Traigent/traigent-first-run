# 0074 - a code answer needs a ruler that scores

Review of the change entry 0071 records found its replacement route unusable,
and running the bundled calibrator confirmed it. The selection table had been
left describing a ruler in prose - compare the answer as text, or gate it
through a parser - and both spellings fail the four-probe gate this same
document makes mandatory. Compared as text, a correct query written with a
different alias scores zero on the equivalent probe. Gated through a parser
alone, every syntactically valid query scores one, so nothing separates a right
answer from a wrong one. Either way calibration exits non-zero, and the card a
customer sees drops to forty-three out of a hundred with two blocking marks.

What these bytes buy is a route with a name and an edge. The row now states the
flag value an assistant is meant to pass, which no document in this package had
ever done for any evaluation method - leaving that choice to be made by matching
prose against help output, where the closest literal match is rated a poor ruler
for a query and the best-rated one is the very call path this guide stops for.
Beside the name goes the property that makes the gate pass: resolve case,
spacing, punctuation and aliases before matching.

The edge is the difference between an author whose calibration passes and one
who widens a scorer until it does. Canonicalizing reaches surface variants,
including an aliased rewrite - measured, not assumed. It cannot reach a join or
subquery of a different shape returning the same rows. An author told neither
thing picks the probe that decides whether their own run is blocked, so the
document now says which equivalents to write and what to do with one it cannot
cover: record it as a coverage gap, rather than loosening the ruler.

The vocabulary file is the other spend. It loads on demand when something is
being explained, independently of the stage document that owns method choice, and
its own rules say a decision the user must make is phrased from its entry. Its
list of evaluator kinds was therefore the menu read aloud at the moment of
choosing, and every route on that menu either ran the answer or was not the one
that scores.

One profile entry moves in the scorer, and it is why a Python-code answer was
worse off than a query. Every other declared kind had at least one well-rated
ruler that does not run the answer; code had none, so guidance could route an
agent at a comparison while the mandated score called that comparison the wrong
one and left the refused path looking like the only good choice. The method that
already covered queries now covers code too. Nothing is removed, so the recorded
card for an executing scorer is untouched, and no band, weight or threshold
moves.
